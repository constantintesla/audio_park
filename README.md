# Audio Park — анализ голоса

Веб-система для исследовательского скрининга голосовых и речевых признаков,
которые могут встречаться при болезни Паркинсона. Приложение проводит врача и
пациента через стандартизированное обследование, проверяет качество записи,
рассчитывает акустические показатели и сохраняет историю наблюдений.

> Система предназначена для исследовательских целей, не ставит диагноз и не
> заменяет консультацию врача или валидированное медицинское изделие.

## Основные возможности

- защищённый вход, роли и разграничение доступа к исследованиям;
- отдельные списки пациентов каждого врача;
- список пациентов с сохранением ФИО в учётной записи и поиском по имени;
- проверка микрофона и калибровка перед обследованием;
- пошаговый протокол из 14 заданий с повторными попытками;
- прослушивание и выбор записей перед отправкой;
- оценка качества записи: шум, клиппинг, длительность и ненадёжные признаки;
- расчёт DSI, jitter, shimmer, HNR, CPPS, F0, темпа речи и пауз;
- сравнение с предыдущими пригодными записями пациента;
- отчёты, графики, аудио отдельных заданий и ZIP-архив обследования;
- экспорт доступных результатов в CSV, JSON и HTML;
- инструкция врача в интерфейсе и в PDF.

## Рабочий сценарий врача

1. Войти в учётную запись.
2. Найти пациента в списке по фамилии, имени или отчеству.
3. Нажать «Выбрать» или «Добавить пациента» → заполнить ФИО → «Сохранить и выбрать».
4. Проверить микрофон и условия записи.
5. Запустить обследование и последовательно выполнить 14 заданий.
6. Прослушать попытки и при необходимости перезаписать отдельные задания.
7. Отправить запись на анализ и открыть результат в истории.

Страница `/guide` содержит краткую инструкцию. PDF-версия доступна по ссылке
«Скачать PDF» на этой странице.

## Пациенты и поиск по ФИО

ФИО сохраняется в SQLite в карточке пациента и доступно в учётной записи врача.
Список сразу показывает ФИО, дату последнего визита и число обследований.
Поиск работает по частям ФИО, без учёта регистра, повторных пробелов и различий Е/Ё.
Выбор всегда выполняет врач. Номер карточки — вспомогательная подпись.

«Добавить пациента» открывает форму с фамилией, именем и необязательным отчеством.
«Сохранить и выбрать» создаёт карточку и оставляет ФИО на экране обследования.
При одинаковом ФИО интерфейс просит подтвердить создание другого человека.
Автоматического объединения карточек нет.

Старым карточкам без имени врач указывает ФИО через «Указать ФИО».
UUID, номер и все связи с обследованиями сохраняются. Исходные имена из старых
HMAC-токенов восстановить нельзя. Старые API токенов оставлены для совместимости,
веб-интерфейс их больше не использует. Миграция SQLite добавляет `full_name` автоматически.

В результатах и экспортах отображается актуальное ФИО связанной карточки.
Доступ к карточкам ограничен владельцем; права на исследования остаются прежними.
ФИО теперь входит в данные приложения и его резервные копии.

### Ключи и резервное копирование

Ключ аккаунта выводится из мастер-ключа `auth_data/patient-hmac.key`, который
хранится отдельно от SQLite. Вместо файла можно задать переменную окружения
`PATIENT_HMAC_MASTER_KEY` — ровно 64 шестнадцатеричных символа.

В резервную копию обязательно должны входить:

- `auth_data/users.sqlite3`;
- `auth_data/session.key`;
- `auth_data/patient-hmac.key`, если ключ не задан через окружение;
- `results.json`;
- каталог `results/`.

Для старых интеграций потеря мастер-ключа не удалит исследования, но повторно введённое ФИО больше
не найдёт старые токены. Сам HMAC-токен является стабильным псевдонимом, а не
юридической гарантией полной анонимизации. Сервер продолжает хранить голосовые
записи и медицинские показатели, поэтому требования к защите таких данных
должны выполняться отдельно.

## Роли и доступ

- `expert` — свои пациенты, обследования, отчёты и экспорты;
- `moderator` — возможности эксперта плюс просмотр всех исследований,
  управление учётными записями и пересчёт результатов;
- `admin` — возможности модератора плюс журнал входов.

Владение исследованием определяется серверной сессией. Переданные клиентом
`owner_id`, `user_id` или имя пользователя не используются для назначения
владельца. Аудио, графики, архивы и детальные результаты проходят ту же проверку
доступа, что и список исследований.

Основные страницы:

- `/` — выбор пациента и новое обследование;
- `/results` — исследования текущего врача;
- `/all-results` — все исследования для старших ролей;
- `/visualization?study=<ID>` — отчёт и визуализация исследования;
- `/guide` — инструкция врача;
- `/users` — управление учётными записями;
- `/auth-logs` — журнал входов администратора.

## Хранение данных

- `auth_data/users.sqlite3` — пользователи, сессии, пациенты и HMAC-токены;
- `auth_data/session.key` — ключ подписи сессий;
- `auth_data/patient-hmac.key` — мастер-ключ поиска пациентов;
- `results.json` — показатели и метаданные исследований;
- `results/<study_id>/` — исходное аудио, калибровка и данные визуализации.

ID исследования имеет формат `AP-<дата>-<случайный UUID>`. Старые строковые
`patient_id` автоматически получают UUID при первом открытии списка пациентов.
Поле `patient_id` пока принимается API для совместимости со старыми клиентами,
но веб-интерфейс использует `patient_uuid`.

Данные времени выполнения исключены из Git. В Docker для них используются
постоянные тома.

## Быстрый запуск

### Docker

```bash
cp env.example .env
docker compose up -d --build
```

Интерфейс: `http://localhost:5000`.

```bash
docker compose logs -f
docker compose down
```

### Без Docker

```bash
pip install -r requirements.txt
python -m app
```

На Windows можно использовать `scripts\START_LOCAL.bat`, на Linux/macOS —
`./scripts/START_LOCAL.sh`.

### Важные настройки

Скопируйте `env.example` в `.env` и проверьте:

- `DEBUG=False` для рабочего сервера;
- `SESSION_COOKIE_SECURE=true` при работе через HTTPS;
- `AUTH_DATA_DIR` — постоянный каталог аутентификации;
- `TRUSTED_PROXY_CIDRS` — только доверенные reverse proxy;
- `SECRET_KEY` — опциональный ключ сессий;
- `PATIENT_HMAC_MASTER_KEY` — опциональный мастер-ключ поиска пациентов.

Если `SECRET_KEY` и `PATIENT_HMAC_MASTER_KEY` не заданы, приложение создаёт
отдельные ключевые файлы в `AUTH_DATA_DIR`.

## Создание и импорт учётных записей

Первичный импорт текстовой выгрузки и создание дополнительного администратора:

```bash
python scripts/manage_accounts.py /private/path/accounts.txt --admin tesla
```

Пароль администратора вводится в скрытом приглашении. Импорт понимает таблицу
`id | email | role | password`, включая хэши Werkzeug `scrypt:32768:8:1`, и
пропускает уже существующие учётные записи.

## API

Все API, кроме healthcheck и получения CSRF до входа, требуют действующую
сессию. Для `POST`, `PUT`, `PATCH` и `DELETE` передавайте `X-CSRF-Token`.

### Авторизация

- `GET /api/auth/csrf` — первичный CSRF-токен;
- `POST /api/auth/login` — вход;
- `GET /api/auth/me` — текущая учётная запись и новый CSRF-токен;
- `POST /api/auth/logout` — завершение сессии;
- `GET/POST /api/users` — управление пользователями для старших ролей;
- `GET /api/admin/auth-logs` — журнал входов администратора.

### Пациенты

- `GET /api/patients` — карточки текущего врача;
- `POST /api/patients` — создание карточки с `full_name` (старые клиенты могут передавать `lookup_token`);
- `PATCH /api/patients/<UUID>` — сохранение или изменение ФИО без изменения связей с исследованиями;
- `GET /api/patients/identity-key` — производный HMAC-ключ аккаунта;
- `POST /api/patients/resolve` — поиск карточек по токену;
- `POST /api/patients/<UUID>/identity` — привязка токена к карточке;
- `POST /api/patients/<UUID>/archive` — архивирование карточки.

### Исследования

- `POST /api/analyze` — анализ и сохранение обследования;
- `GET /api/results` — доступные исследования и фильтры;
- `GET /api/results/<study_id>` — одно исследование;
- `GET /api/visualization/<study_id>` — данные визуализации;
- `GET /api/audio/<study_id>` — полная запись;
- `GET /api/audio/<study_id>/task/<n>` — запись отдельной попытки;
- `GET /api/archive/<study_id>` — ZIP обследования;
- `GET /api/stats` — статистика;
- `POST /api/recalculate-all` — пересчёт результатов для старших ролей;
- `GET /api/export/csv|json|html` — экспорт доступных исследований;
- `GET /healthz` и `GET /api/health` — healthcheck.

`POST /api/results` намеренно отключён: результат сохраняется только внутри
`POST /api/analyze`.

`GET /api/results` поддерживает `scope`, `q`, `patient_id`, `owner_id`,
`date_from`, `date_to` и `limit`. `scope=all` доступен только старшим ролям.

## Протокол обследования и анализ

Веб-интерфейс записывает один полный прогон и передаёт границы отдельных
попыток. Режим `task=exam` объединяет задания DSI и речевой протокол:

- `mpt` — протяжная «а» на одном выдохе;
- `glide` — скольжение до высокой ноты;
- `soft` — самый тихий устойчивый голос;
- `vowel` — спокойная протяжная гласная;
- `reading` — чтение текста;
- серии слогов, фразы с разным темпом и интонационные задания.

Границы передаются в `dsi_segments` и `protocol_segments`. По протяжной гласной
оцениваются jitter, shimmer, HNR и CPPS; по чтению — интонация, громкость, темп и
паузы. Признаки, которым нельзя доверять из-за качества записи, перечисляются в
`quality.unreliable_features`.

DSI рассчитывается по формуле:

```text
DSI = 0.13 * MPT + 0.0053 * F0-High - 0.26 * I-Low - 1.18 * Jitter(%) + 12.4
```

Абсолютный `I-Low` зависит от калибровки. Если точной поправки dBFS -> dB SPL
нет, результат помечается как приближённый. DSI описывает качество голоса и сам
по себе не подтверждает наличие или стадию болезни Паркинсона.

Для сравнения с личной историей блок `baseline` использует медиану предыдущих
пригодных записей того же пациента и владельца. До накопления достаточного числа
записей возвращается статус `collecting`.
