# План: загрузка аудио частями и сборка на сервере

Дата: 7 ноября 2026 года. Статус: план, изменения приложения ещё не выполнены.

## Решение

Первый переход меняет только передачу и надёжность сохранения аудио.
Браузер передаёт существующую запись небольшими частями, сервер собирает исходный
WAV без изменения звука и вызывает существующий анализатор.

Промежутки между заданиями, фоновые звуки и заменённые попытки сохраняются
в общей дорожке. Границы актуальных попыток по-прежнему определяют, какие
участки участвуют в расчётах заданий. Калибровка остаётся отдельной записью.

Это разбиение потока на транспортные части, а не переход на анализ каждого
задания отдельным файлом. Объём одного запроса уменьшается; общий объём записи
и стоимость анализа от этого не уменьшаются.

Почему сохраняем дорожку: app/parkinson_analyzer.py выполняет нормализацию
громкости и оценку качества до выделения заданий. Удаление промежутков меняет
входные данные этих операций. В первом переходе методику анализа не меняем.

## 1. Зафиксировать контракт и контрольные записи

- Добавить версию протокола загрузки и согласовать состояния:
  uploading → assembling → queued → analyzing → completed; отдельно failed и cancelled.
- Идентификатор загрузки выдаёт сервер. Привязка к владельцу и пациенту
  фиксируется при создании; все операции повторно проверяют права и CSRF.
- Манифест содержит версию, формат PCM, частоту, каналы, общее число отсчётов,
  размер и SHA-256 каждого куска, порядок частей, метаданные устройства,
  актуальные границы заданий и ссылку на калибровку.
- Долгая «а», используемая двумя протоколами, остаётся одной записью с двумя
  ссылками в разметке. Не дублировать её звук.
- Подготовить контрольные записи с длинными промежутками, перезаписями,
  тихими попытками и разными поддерживаемыми частотами.

Готово, когда контракт описан, а для контрольных записей сохранены исходные
WAV, разметка, версия анализатора и результаты прежнего пути анализа.

## 2. Реализовать сервер загрузок отдельно от анализатора

Предлагаемый API:

- POST /api/uploads — создать загрузку обследования.
- PUT /api/uploads/{id}/parts/{number} — передать часть.
- GET /api/uploads/{id} — получить состояние и список принятых частей.
- POST /api/uploads/{id}/complete — зафиксировать манифест и запустить сборку.
- POST /api/uploads/{id}/cancel — отменить незавершённую загрузку.

На первом этапе резать готовый WAV по байтам в браузере, например на части
по 4 МиБ, и склеивать эти байты на сервере в исходном порядке. Части не являются
самостоятельными WAV; заголовок есть только в исходном файле. Такой вариант
позволяет получить побайтово тот же WAV без повторного кодирования.

- Загружать с ограниченной параллельностью, начать с двух запросов.
- Записывать часть во временный файл, проверять размер и хэш, затем атомарно
  переводить её в состояние принятой. Хранить состояние загрузок в SQLite,
  файлы — в постоянном каталоге на подключённом томе.
- Повтор той же части с тем же содержимым возвращает успех; с другим
  содержимым — конфликт. Часть не перезаписывается незаметно.
- Проверять фактический объём потока; не доверять Content-Length, имени файла,
  расширению, заявленной длительности и хэшу без проверки содержимого.
- Проверять владение загрузкой для каждой операции. UUID не заменяет права.
- Лимиты на одну часть, совокупный объём, число частей и активных загрузок
  задаются отдельно. Числа для общего объёма и длительности выбрать после
  нагрузочной проверки; лимит части согласовать с nginx с запасом.
- Калибровку загрузить как отдельный объект с теми же проверками и привязкой
  к обследованию. Смена устройства требует отдельного решения по калибровке.

Готово, когда потерянный ответ, повтор запроса, загрузка не по порядку и
перезапуск приложения не приводят к дублированию или повреждению частей.

## 3. Собирать исходный WAV и подключить существующий анализ

- complete атомарно фиксирует манифест. После этого части и разметка неизменяемы.
  Параллельный или повторный complete возвращает тот же идентификатор задания.
- Проверять наличие всех частей, порядок, размеры и хэши. Неполную загрузку
  не передавать анализатору.
- Собирать файл потоково на диске, не загружать всё аудио в память ради склейки.
- Проверять хэш итогового файла, его декодируемость, фактическую частоту,
  каналы, число отсчётов и допустимость границ попыток.
- Сохранить паузы и все отсчёты без обрезки, нормализации, ресемплинга и
  повторного кодирования на этапе сборки.
- Вынести общий вызов анализа и сохранения результата из обработчика
  /api/analyze в сервисную функцию. Старый API и новый путь вызывают её.
- Анализ выполнять вне запроса complete. Для одного сервера достаточно
  сохраняемой в БД очереди с отдельным worker и ограничением параллельности.
  После перезапуска восстанавливать задания без создания второго результата.
- Идентификатор результата выделять один раз; сохранение результата сделать
  идемпотентным и учесть сбой между записью результата и обновлением статуса.
- Браузер получает состояние задания и ссылку на результат через API статуса.

Готово, когда собранный WAV побайтово совпадает с исходным, границы заданий
не меняются, а одинаковый вход в той же версии анализатора даёт эквивалентный
результат. Допуски для недетерминированных вычислений фиксируются заранее.

## 4. Переключить браузер на новую передачу

- Сохранить существующий сценарий записи, проверки и перезаписи заданий.
- После подтверждения обследования формировать тот же examination.wav,
  нарезать Blob на части и передавать через новый API.
- Показывать раздельно: сохранено частей/байтов, сборка, ожидание, анализ,
  результат. Прогресс загрузки отражает подтверждённые сервером байты.
- Повторять временные сетевые ошибки с задержкой. При 401/403 сохранять
  доступные данные и предлагать восстановить вход; не повторять бесконечно.
- При возобновлении запрашивать уже принятые части и досылать отсутствующие.
- Непонятный или HTML-ответ сервера преобразовывать в понятное сообщение,
  проверяя HTTP-статус и тип содержимого до разбора JSON.
- До завершения сохранять возможность скачать исходную запись.

Для восстановления после обновления вкладки сохранять исходный Blob,
upload_id и манифест в IndexedDB. Это локальные чувствительные данные:
разделять по пользователям, не показывать другому вошедшему пользователю,
очищать после подтверждённого сохранения или явной отмены. Проверять доступную
квоту; при невозможности локального сохранения явно сообщать, что восстановление
после закрытия вкладки недоступно, и предлагать скачать файл.

Готово, когда обследование больше 50 МиБ проходит новым путём, а потеря сети
и обновление вкладки не требуют повторного прохождения при наличии локальной копии.

## 5. Проверить совместимость и ограничения ресурсов

- Старые обследования, /api/analyze, прослушивание, архивы и пересчёт работают
  без миграции ранее сохранённых WAV и временных границ.
- Проверить 48 и 44,1 кГц, паузы, повторные попытки, калибровку, отсутствие
  файла, повреждённый заголовок и части с неверным размером/хэшем.
- Проверить доступ к чужой загрузке, CSRF, повтор complete, параллельные
  запросы, обрыв во время сборки/анализа и заполнение диска.
- Расширить scripts/test_recorder.cjs, scripts/test_access.py,
  scripts/test_exam_archive.py; добавить проверки протокола загрузок
  и выполнить scripts/ci_smoke.py.
- Проверить память и время на длинных записях в условиях production
  mem_limit=1536m. Склейка на диске не отменяет затрат анализатора на весь WAV.
- Проверить поведение при превышении общего безопасного лимита: запись
  остаётся доступной для скачивания, пользователь не получает ошибку JSON.

Готово, когда контрольные результаты совпали, ошибки восстановления проверены,
а общий допустимый объём подтверждён измерениями. Загрузка частями сама по себе
не означает поддержку аудио произвольной длины.

## 6. Включить постепенно и обеспечить откат

- Перед выкладкой сделать резервную копию результатов и БД; проверить
  восстановление. Новый каталог загрузок добавить в постоянные тома.
- Сначала выложить серверный API и worker при выключенном новом интерфейсе.
- Включить загрузку частями флагом для тестовых учётных записей, затем для всех.
- Записывать технические события с upload_id: размеры, число повторов,
  длительность сборки/анализа, ошибки, использование диска. Не писать звук,
  пароли, токены и персональные данные в технические журналы.
- Откат флага останавливает создание новых загрузок через новый интерфейс;
  уже начатые загрузки и задания сервер продолжает обслуживать.
- Очистку незавершённых загрузок запускать по сроку неактивности, исключая
  assembling/queued/analyzing и принятые результаты. Сначала проверить её
  в режиме отчёта без удаления. Срок хранения определить явно до включения.
- После успешного результата временные части удалять только после проверки
  сохранённого исходного WAV и ссылок результата.

Готово, когда новый путь стабилен, начатые загрузки переживают откат интерфейса,
а временные файлы не растут бесконтрольно.

## Следующий этап, отдельно от первого перехода

Первый релиз по-прежнему держит полную запись в памяти браузера и начинает
загрузку после подтверждения. Он устраняет большой единичный запрос и позволяет
возобновлять отправку, но не защищает ещё не сохранённый черновик во время теста.

Дальше можно сохранять PCM-блоки в IndexedDB и отправлять их уже по ходу
обследования. Записывать весь звук между заданиями, сохраняя прежнюю временную
шкалу. Общий WAV-заголовок сервер создаёт по окончательному числу отсчётов;
воспроизведение отдельных попыток читает нужные блоки. Это отдельное расширение
протокола с проверкой побайтовой/посэмпловой эквивалентности.

Переход на хранение только актуальных попыток, удаление промежутков и изменение
методики нормализации в этот план не входят. Для них нужна отдельная валидация
измерений. Также отдельно рассматривается замена ScriptProcessorNode.

## Рекомендуемые порции реализации

1. Контракт, состояние загрузок, приём частей, проверки доступа и тесты.
2. Сборка без изменения WAV, сохраняемая очередь, общий сервис анализа.
3. Браузерная загрузка, повторы, IndexedDB и понятные ошибки.
4. Проверки эквивалентности и ресурсов, флаг включения, документация и очистка.

Каждая порция должна сохранять работоспособность прежнего пути. Включение
для пользователей — только после прохождения всех критериев этапов 1–5.
