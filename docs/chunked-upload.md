# Загрузка WAV частями (протокол v1)

Реализован первый переход из `chunked-upload-plan.md`: готовый examination.wav
режется по байтам после подтверждения обследования. Запись, паузы, заменённые
попытки, временная шкала, нормализация и анализ не изменены. Калибровка передаётся
отдельным WAV в той же загрузке. Общая долгая «а» содержит один участок звука,
на который ссылаются оба списка разметки.

## API

Все операции требуют действующей сессии. POST/PUT требуют X-CSRF-Token.
Каждая операция проверяет владельца загрузки и пациента; менеджер не получает
доступа к чужим незавершённым записям. Идентификатор результата назначается
при создании загрузки и больше не меняется.

- `GET /api/uploads/config`: флаг интерфейса и пределы.
- `POST /api/uploads`: `{version:1, patient_uuid, client_token?}` → `upload_id`.
  `client_token` — случайный ключ клиента для безопасного повтора при потере
  ответа, уникальный в пределах владельца. Привязка пациента неизменяема.
- `PUT /api/uploads/{id}/parts/{number}`: сырые байты, X-Part-Size,
  X-Part-SHA256 (SHA-256 в нижнем регистре). Нумерация с нуля, общая для обоих
  WAV. Повтор идентичной части успешен, другие байты дают 409. Части не являются
  отдельными WAV. Проверяется фактически прочитанный поток.
- `GET /api/uploads/{id}`: `state`, `parts:[{number,size,sha256}]`, `error`,
  `study_id` после completed. Результат доступен через прежний API результатов.
- `POST /api/uploads/{id}/complete`: манифест → 202, `job_id`.
  Неполный набор частей даёт 409 и остаётся редактируемым. После фиксации
  манифест и части неизменяемы. Повтор идентичного complete возвращает тот же
  job_id; отличающийся манифест даёт 409, в том числе после завершения.
- `POST /api/uploads/{id}/cancel`: отменяет uploading/failed, повтор безопасен.
  Начавшиеся сборка/анализ не прерываются. Для completed возвращает подтверждение
  сохранения без изменения результата; это позволяет удалить локальный черновик.

Манифест (все размеры в байтах; samples — число кадров на канал):

```json
{
  "version": 1,
  "files": {
    "recording": {
      "format": "pcm_s16le", "sample_rate": 48000, "channels": 1,
      "samples": 48000, "size": 96044, "sha256": "<SHA-256 всего WAV>",
      "parts": [{"number": 0, "size": 96044, "sha256": "<SHA-256 части>"}]
    }
  },
  "device_info": {"task": "exam", "dsi_segments": [], "protocol_segments": []},
  "calibration": {}
}
```

`files.calibration` при наличии имеет ту же структуру. Порядок элементов parts
задаёт порядок байтов внутри соответствующего файла. Номера не повторяются
между файлами. Все принятые части должны быть использованы. Ограничены также
размер манифеста (128 КиБ) и число элементов разметки (500 на протокол).

Worker потоково собирает WAV на диске, проверяет каждую часть, общий хэш,
PCM-заголовок и фактическое число читаемых кадров. Разметка проверяется по
числу отсчётов/частоте. Сборка ничего не вырезает и не перекодирует.

## Очередь и процессы

`python -m app.upload_worker` запускает отдельный процесс. API только принимает
данные и фиксирует задание. SQLite и части хранятся в UPLOAD_DIR (по умолчанию
AUTH_DATA_DIR/uploads); каталог должен быть на постоянном локальном томе.
Сетевые файловые системы и несколько серверов этим решением не поддерживаются.

Состояния: uploading → assembling → queued → analyzing → completed;
также failed и cancelled. queued фиксируется после проверки WAV перед анализом.
Worker держит OS-lock на всё время жизни: второй worker с тем же томом
не запускается. После завершения процесса блокировка снимается ОС. Новый
worker подбирает assembling/queued/analyzing. Сохранённый результат с тем же
study_id повторно не анализируется, даже при сбое перед фиксацией completed.

Старый `/api/analyze` и очередь вызывают общий `analyze_and_save`. Анализ через
эти два пути, массовый пересчёт и построение визуализаций сериализованы общей
файловой блокировкой: одновременно выполняется одна тяжёлая операция на сервер.
Загрузка частей продолжает работать во время анализа. Лимиты контейнеров API и
worker по 1536m действуют отдельно; это не общий лимит памяти всего сервиса. Индекс результатов
защищён между процессами и сохраняется атомарной заменой файла. Исходный и
калибровочный WAV сверяются с манифестом после сохранения. Только затем
фиксируется completed и удаляются временные части. При ошибке остаётся failed,
части сохраняются для разбора. После исправления причины администратор может
перевести failed с сохранённым манифестом обратно в assembling в SQLite при
остановленном worker; нового идентификатора результата не создавать.

## Браузер и восстановление

Два параллельных PUT; максимум три повтора временной ошибки с задержкой
0,5/1/2 с. 401/403 не повторяются. Для восстановления сессии следует войти
в отдельной вкладке и нажать «Продолжить отправку»; CSRF обновляется перед
возобновлением. Процент отражает только подтверждённые байты. Сборка, ожидание
и анализ показываются отдельными состояниями без придуманного процента анализа.

IndexedDB `audio-park-uploads/drafts` хранит Blob, манифест, client_token и
upload_id отдельно по ID пользователя. После обновления страницы появляется
панель продолжения. Она работает и после отключения флага. У другого пользователя
свои черновики; при смене аккаунта в другой вкладке проверка сессии перезагружает
страницу. Локальная копия удаляется после подтверждения результата или явной
отмены. При нехватке квоты/ошибке IndexedDB показывается сообщение, что закрытие
вкладки лишит возможности восстановления. Скачивание доступно из панели до
завершения. Одновременно поддерживается один локальный черновик на пользователя.

## Включение, данные и откат

По умолчанию `CHUNKED_UPLOAD_ENABLED=false`; тестовые логины задаются через
`CHUNKED_UPLOAD_USERS=doctor1,doctor2`. `true` включает интерфейс всем.
API и worker обслуживают начатые задания независимо от флага.

Docker Compose запускает API и worker с общими томами результатов и auth.
У worker тот же образ `audio_park-api:latest` и лимит памяти 1536m.
**Изменение хранения индекса:** прежний одиночный bind-mount results.json
не допускает атомарной замены. При первом запуске контейнера валидный старый
индекс копируется в `/app/auth/results.json`, только если нового ещё нет.
Далее актуальный индекс — `data/auth/results.json` (prod) либо
`auth_data/results.json` (dev); исходный results.json остаётся источником
первого импорта, доступным контейнеру только для чтения. WAV не перемещаются.
Не удалять новый индекс ради «повторного импорта».

Перед выкладкой остановить запись, сделать и проверить резервную копию старого
results.json, results/, всего auth/ (БД, ключи, новый индекс и uploads).
Первый запуск проверить при выключенном флаге: число старых исследований,
прослушивание, архив и доступ владельца. Затем тестовые аккаунты, затем общий
флаг. Откат интерфейса — отключение флага; API и worker оставить работающими.
При откате к старому образу сначала остановить оба процесса и восстановить
актуальный auth/results.json на прежнее место results.json; иначе старый образ
увидит устаревший индекс. Сохранять uploads для последующего продолжения.

Пределы v1: часть 4 МиБ, 128 частей, 3 активные загрузки на пользователя,
общий размер по умолчанию 96 МиБ (включая калибровку), длительность каждого WAV
900 с, PCM16, 1–2 канала, 8–96 кГц. Общий размер и время настраиваются
UPLOAD_MAX_BYTES/UPLOAD_MAX_SECONDS. Это предварительные потолки, а не результат
production-нагрузочного теста; до измерений не включать всем. Для нового API
nginx должен принимать часть с запасом (например, отдельный location для
`/audio_park/api/uploads/` с `client_max_body_size 5M`); старому API оставить
согласованный с Flask общий лимит. Клиент объясняет также HTML-ошибки прокси.

Срок неактивности черновиков — 7 суток. Сначала выполнить
`python scripts/cleanup_uploads.py` (только отчёт), затем при проверенных
резервных копиях `python scripts/cleanup_uploads.py --delete`. Запускать с теми
же AUTH_DATA_DIR/UPLOAD_DIR, что у сервиса, например ежедневно через системный
планировщик. assembling/queued/analyzing/completed не удаляются. Оставшиеся
после аварии завершённые каталоги worker очищает при запуске после повторной
проверки ссылок/хэшей сохранённого результата; при ошибке оставляет для разбора. Следить за свободным местом постоянного тома.
События upload_created/upload_part/upload_completed/upload_failed содержат ID,
размеры, повторы и время, без аудио или токенов.

## Проверки и границы проверки

- `python scripts/test_uploads.py`: доступ, CSRF, повторы, SHA/размеры,
  неполный манифест, лимиты, гонка complete, 44,1/48 кГц, калибровка,
  эквивалентность байтов, сборка WAV 52 МиБ (пик Python-памяти около 3 МиБ), имитация заполненного
  диска и повтор worker после записи результата.
- `node scripts/test_recorder.cjs`: прежний сценарий 14 заданий/27 попыток,
  перезапись и сохранение всей временной шкалы в WAV.
- `node scripts/test_upload_client.cjs`: реальные функции клиента с имитацией
  сети/IndexedDB, потерянный ответ, две отправки, квота, ошибки авторизации/HTML.
- `python scripts/ci_smoke.py`: настоящий анализатор, прежний API, новый worker,
  эквивалентность признаков/разметки/исходных байтов на синтетическом обследовании.
- `python scripts/test_exam_archive.py reference.zip`: проверяет оба пути на
  контрольном архиве обследования. Численные признаки: rtol=1e-5, atol=1e-6;
  DSI: абсолютный допуск 0,05. Сохранять исходный ZIP, результаты старого пути
  и git revision анализатора с контрольным набором вне Git.

Без предоставленного контрольного архива сравнение на настоящем обследовании
не выполняется. Также отдельно нужны production-замеры RSS/времени на длинной
записи в 1536m, аварийное завершение контейнера, заполнение тома и восстановление
резервной копии. Успех транспортного теста не подтверждает возможность анализа
аудио произвольной длительности. Запись ещё не подтверждённого обследования
по-прежнему находится в памяти браузера; потоковая запись во время теста —
следующий этап плана.
